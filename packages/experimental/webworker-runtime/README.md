# `@deepseek-ai/dsh-experimental-webworker-runtime`

English | [中文](README.zh.md)

## Summary

The browser worker host: the whole harness plugin tree runs inside one dedicated Web Worker, for preview deployments and packaging regressions ([experimental group](../README.md)). The worker inflates a packed VFS image off its download and mounts it in memory, loads its modules through a CommonJS wrapper loader, and serves the page over a postMessage tunnel that speaks plain HTTP. Use it when a preview must run the packaged harness without a Node host.

## Use this package

The public npm package exposes the runtime library at its root, the self-contained browser Worker at `./worker`, and the page connector at `./client`. Deployments supply and serve the VFS image separately through the [packer](../webworker-packer/README.md); installing this library does not add a profile layer. The root also exports the module-proxy and replacement tables used by the packer.

Three build artifacts and one source-owned process layer:

- **`lib/index.js` (assembly library)** — `createWorkerHost`/`startWorkerHost` mount the base image and any ordered data overlays (`storage/`), register the image's lazy archives, install the module loader (`module-system/`) and the `process` shim, boot the tree through the image's own `dsh-app-boot`, and hand the tunnel its serving seams. Overlays may replace files only under `home/` and `workspace/`; they cannot replace the base manifest or modules. The image layout contract (`image-layout.ts`: virtual root, manifest path, lazy archive directory, empty directories) and the manifest (`image-manifest.ts`: profile, installation, the `lowered` wrapper-contract gate, lazy archives) are shared with the packer. The Worker boots the manifest's shipped profile as the launcher does: the image's app-boot initializes `home/profiles/<profile>/` from the shipped template, resolves bundles from the installation manifest the image carries alone, and composes the bundle layers, the profile patch, and the home patch. The profile context, the launch environment snapshot, and a `PluginPackages` service without a runtime resolution are provided as the launcher provides them; the Worker loader owns module resolution. The profile context carries no command-line overlay; the image's home patch (`home/cordis.patch.yml`), which the packer writes from `PLATFORM_ENTRY_CONFIG`, keeps JSONL Session logs plaintext. ConfigEditor persists overrides in the profile patch, reconciles each write, and Loader commits live values. The Worker commits `appReady` once the tunnel serves. Its `hmrModules` provider connects the Worker module cache to [profile HMR](../../boot/hmr/README.md), so configuration and loaded code changes share the existing reload queue. Plugin management lists and switches the installation's optional bundles, and its package operations fail with the `execa` refusal. Without a persistence controller, configuration edits last for the current Worker lifetime.
- **Lazy archives** — the manifest registers each page chunk the packer moved out of the base image by path and size, with its archive name relative to the image URL. Existence, stats, and listings answer at once; the first asynchronous read (`fs.promises.readFile`, `fs.promises.open`, `fs.createReadStream`, `fs.promises.cp`) fetches and inflates that archive once for every waiting reader, checks it against the registration, and mounts its files without publishing a mutation. A failed fetch rejects the read and leaves the files registered, so the next read fetches again. Until then, synchronous reads, writes, appends, truncation, chmod, rename, and link of a registered file fail with `ERR_DSH_VFS_DEFERRED` naming the archive; unlink and recursive removal drop the registration, and seeding the path replaces it. The archive name derives from its content digest, and the fetch checks only the registered paths and sizes, not the digest. An image that registers lazy archives must be passed as a URL.
- **`lib/worker.js` (worker bundle)** — the assembly plus this package's Node-compatibility layer as one self-contained ES module. The module proxy table (`module-proxies.ts`) is the only platform fork: `node:*` builtins over VFS/tunnel/browser primitives, structural stubs that fail loud on the console for what a browser cannot do, and native/binary package replacements. `node:module` supplies `createRequire().resolve` and `.resolve.paths()` over the image package root, so unchanged packages can discover manifests without evaluating their modules. `node-addon-require-builtin` answers the Node v24.18.0 internal modules that the vendored Loader, app-boot, and HMR read without `--expose-internals`: the cascaded ESM loader's `resolveSync` and `import` over the Worker loader, with Node's `ERR_MODULE_NOT_FOUND` and `ERR_PACKAGE_PATH_NOT_EXPORTED` codes, and an empty `loadCache`; and the CommonJS loader, package reader, `modules` binding, and resolve-cache members that HMR replaces, which refuse when called. `process.versions.node` reports `24.18.0`, so `ModuleLoader.fromInternal()` and the Loader's `internal` reach that cascaded loader. `node:path.win32.isAbsolute` and `node:util.inherits` follow Node; other `win32` members throw. The `node:util` JSON-data comparator compares own enumerable properties, preserving Node admission decisions for recorded fields such as `__proto__`. The global `process` shim carries Node detection fields including `title`, preventing Worker execution from entering DOM-only branches. The pack-time parser reports statically named module requests, including module-scope direct calls of the form `createRequire(import.meta.url)('pkg')` through a named `node:module` or `module` import, to the packer's reachability walk. Stored, CommonJS-obtained, and rebased `createRequire` calls require image entry seeds. VFS mutations drive `node:fs` callback, polling, and promise watchers, whose listeners run in the async context where the watcher was created rather than that of the writing code; open descriptors retain file identity and access mode across rename, replacement, and unlink, `FileHandle.stat({ bigint: true })` reports the same device and inode identity as a path stat while the name still refers to that file, and `FileHandle.chmod()` updates the opened file identity; `readable-stream` supplies `node:stream/promises` completion and pipeline helpers and the stream state machine used by file streams and unchanged image packages such as Chokidar and readdirp. `node:string_decoder` uses the maintained npm decoder to retain incomplete UTF-8 and UTF-16 characters across stream chunks. AsyncLocalStorage carries sync-stack causality across `await` through the snapshot/restore faces the pack-time lowering injects. The worker holds no compiler: an image the packer did not lower is refused at mount. The callback `fs.realpath.native` alias resolves within the mounted VFS and supports `util.promisify`.
- **`src/shell/` (the worker's own process layer)** — a browser worker cannot fork, so `node:child_process` is not a stub but an implementation: `spawn` starts the command in its own Web Worker — this same bundle, told by its first frame to be a shell process — and reports it through the `ChildProcess` surface the subprocess service consumes. The command runs off the host's thread, `SIGKILL` terminates it whatever it is doing, and filesystem and registered-host-command requests reach the host by message. Shell exit waits for accepted host operations to settle after cancellation. Worker platform executables preserve native-package protocols such as Landlock without replacing their JavaScript packages or coupling their implementations to `node:child_process`; `xdg-open` sends one VFS text file to the page's read-only viewer, so desktop-opener actions such as **Open configuration file** show the file in the page; ordinary commands use the package's evaluator and coreutils command table. The grammar is `@yarnpkg/parsers`' `parseShell`, while `execSync`/`fork` still refuse because they need a real process.
- **`lib/client.js` (page half)** — startup has two independent stages. `chooseWorkerHostSource({ image?, fixtureManifest? })` optionally owns the boot barrier and fixture manifest: without `preview-fixture` it waits at the source chooser, while a valid query selects directly; either path returns ordered overlays. `connectWorkerHost(worker, { image?, overlays? })` remains the public base-runtime connector; callers that skip the chooser get an empty overlay list. `apps/web` invokes both and supplies its statically bundled Worker. The opening `init` frame carries the base and ordered overlay URLs, the boot payload delivers the structured index-injection table, and `applyIndexInjections` executes it before the shell entry runs. Script preload rows are advisory and skipped because `/plugins` resources resolve only through the tunnel; `loadBundle` fetches each combo on first demand, embeds its tunnel-only source map as a Base64 data URL, and executes the script as a Blob. The worker's unsolicited `view-text` frame opens the page's modal text viewer. The tunnel also exposes fetch-shaped transport, the independent file-upload carrier, and the API client. Request frames preserve Blob bodies through structured clone and transfer `ReadableStream<Uint8Array>` ownership. The Host Worker streams both forms into the route, so neither browser thread creates a complete byte array for a generic-file upload. A Remote stream's uplink crosses as `stream-uplink-item` / `stream-uplink-end` frames into an unbounded `TunnelUplink` that drops items arriving after `end`: the page and its worker are one trusted same-origin boundary, so the Host inbox cap does not apply.

Callbacks and timers registered under an explicit root context retain its empty stores, so they cannot inherit an unrelated transaction.

Acceptance lives in `apps/web/tests/preview-boot.e2e.ts`, which serves the real built pages and drives the pre-boot chooser plus Worker activation in headless Chromium. The empty selection exercises first-run startup. The `vfs-example` overlay supplies ordinary workspace files and plaintext persistence artifacts for cold Workspace/Session discovery, tool presentation, subagent navigation, and history paging without a model request. The showcase mixes empty, whitespace-only, and non-empty reasoning with a long multiline command and a parent-path file link; these are authored fixtures, not live model output. The [packer](../webworker-packer/README.md) prepares current-generation successors from committed historical logs in Node; those source logs remain byte-identical in the overlay. The fixture generator owns the acceptance test's current projection cache. The chooser reserves WebFS as a separate user-authorized source; that provider does not read the built-in fixture.

The [built-bundle import sweep](tests/compile/transform-corpus-check.ts) checks bare Node imports after the library build. Its Dockkit exception accepts Node’s unknown-`.css`-extension refusal for any stylesheet rather than one pinned path; another extension, error code, or message, and an unexpectedly successful exempt import, remain errors.

<a id="aiw-workbench"></a>
## AIW workbench

The Worker-local `/__aiw/status` and `/__aiw/action` endpoints support the AIW management page. Files and source projects remain in the VFS. Text edits require the digest of the last observed contents before overwriting an existing file; new-file writes never replace an existing file. The editor accepts UTF-8 files up to 1 MiB. Application profiles, Session files, credential paths, immutable artifacts and the internal history store cannot be mutated through these operations. Base packages can be browsed read-only. File operations and the limited command line share these access rules; hard-linked aliases are rejected.

Plugin installs retain verified, content-addressed artifact bytes before replacement or garbage collection, including installs and removals initiated through the existing CLI. Source builds also retain the exact selected sources and normalized descriptor. History survives with the existing home-directory persistence provider. A revision records its actual Host activation outcome separately; retained code does not establish Client activation. Restoring uses the ordinary integrity checks, installer and HMR queue and can work with Forge offline. A plugin installed before workbench history exists has no earlier source snapshot; its current artifacts are captured before replacement or removal.

File backups preserve original binary bytes and directories, validate every path and digest before mutation, and import only into an empty workspace subdirectory. Plugin backups include a manifest, verified artifact objects and optional source. Imported plugin source is written to a new workspace directory rather than overwriting an existing project. Backup limits are 1,000 files and 32 MiB; protected credential files and internal caches are excluded. These backups cover selected files or plugin projects, not a live whole-profile or Session-state restoration.

The command line runs the existing VFS shell and virtual `dsh`, without OS processes or a Node package manager. Each request starts in its selected working directory, has a 30-second deadline and a 1 MiB output limit, and is cancelled when the workbench closes. Commands can report nonzero exit codes inside a successful HTTP response. Saving files or restoring a plugin does not itself confirm browser persistence; use the storage flush action before closing the page.

<a id="browser-persistence"></a>
## Browser persistence

The preview establishes the shell boot barrier before loading the storage UI module; the shell waits for Worker injections before reading its module-loader facade. The Forge preview enables IndexedDB storage by default; `?storage=none` selects an ephemeral Worker without clearing saved data. The dsh-aiw page header reports pending, saved or failed filesystem writes and provides **Save now**. Startup and terminal storage failures also remain visible globally. The page transport exposes status subscriptions and explicit flush through `WorkerStorageControls`. The explicit flush action first drains buffered Session events through the mounted Session persistence service, then waits for browser storage; a Session flush failure stops confirmation. Automatic filesystem status alone does not acknowledge events still buffered by that service. Saved means the storage transaction completed; successful synchronous filesystem writes alone do not confirm persistence. Page unload is not used as a save guarantee. After writes are saved, a reload restores plugin installations, native enabled/disabled selections, configuration, Session files and workspace files before Cordis starts.

`VfsPersistenceController` connects the VFS mutation sink to a replaceable `VfsPersistenceProvider`. Only runtime changes under `home/` and `workspace/` enter the store; base-image modules and untouched template files remain supplied by the static image. `IndexedDbVfsProvider` stores node metadata and 64 KiB file chunks separately. Subsequent appends write the changed tail and new chunks, while tombstones preserve deletions across reconstruction from the base image. Permissions and recorded modification times are restored; hard-link inode identity is not retained across Worker lifetimes. The Session log format is unchanged. Hydration still reconstructs these files in RAM; this provider does not make the VFS disk-backed. In-flight requests, plugin variables and transient DOM edits are not restored.

Storage namespaces include the storage schema, embedded Forge generation, deployment and selected image/overlay source. Browser origins additionally isolate their own databases. Another generation or source selects a separate namespace and retains the previous data; no automatic migration or cross-version plugin loading occurs. The provider atomically compares revisions before applying an operation group. A stale tab stops mirroring with `STORAGE_CONFLICT`, preserving the newer committed data. Storage failures leave current in-memory changes available but unconfirmed; the failure notice remains visible and the controller does not retry implicitly. An invalid stored snapshot or Forge catalog prevents boot and is retained rather than replaced with defaults. Saved immutable `.forge/packages` artifacts must retain their recorded hashes; editing those bytes directly prevents catalog restoration.

The Forge catalog records applied manifests and retained artifact ownership, independently of activation. Installation groups code, generated package metadata, profile registration and the catalog in one synchronous persistence batch before awaiting Cordis reconciliation. Removal first deselects and unloads the plugin, then groups file collection and catalog removal. A fresh Worker validates saved artifacts and restores importer mappings before profile composition; native Loader state determines activation afterward. Installed packages can therefore start without contacting Forge; loading the base image and page still requires their static resources. The catalog and controller implementations own these operations in [forge/catalog.ts](src/forge/catalog.ts) and [storage/persistence.ts](src/storage/persistence.ts).

The current provider uses browser-local storage. It does not implement native RPC storage, cloud synchronization or cross-tab merging. File and plugin archive operations belong to the [AIW workbench](#aiw-workbench). Clearing site data removes it, and browser quota or storage eviction remains browser-owned. Callers of `createWorkerHost` opt in by passing a controller through `persistence`; without one the host remains ephemeral. The controller owns its provider until disposal, settles queued writes and closes the provider after host teardown.

## Forge plugin updates

The optional preview control opens with `?forge=<HTTP service URL>`. **DSH Forge** submits local Host/Client plugin sources or an npm package specification to that service and applies its compiled manifest through the running Worker. The rc.2 frontend embeds `FORGE_GENERATION = 'dsh-worker-rc2-8'`; it rejects artifacts from other generations before downloads or writes. The service must target that generation and the base image's exact host package versions. Core packages and shared host modules remain owned by the frontend build. The target separately declares `clientPackages`, captured from the trusted base image before overlays; these exact page-shared versions satisfy Client requirements without granting Host imports. Missing or mismatched Client requirements and attempts to replace shared Client packages fail before file writes. Published packages with a supported single-entry `dsh.bundle` patch can carry their existing Client bundle; package metadata and assets enter the normal Client graph and HMR path.

The installer verifies the complete manifest, supported bundle patch and missing artifact bytes before changing files. Supported bundle patches contain exactly one `insert` of their own package, with `id`, `name`, and optional JSON-compatible literal `config` (objects, arrays, scalars or null), whose schema is validated by the plugin. The same patch may override existing root entries using unique `id` values and literal `config`, `disabled` (boolean or null), or both. Overrides cannot target the inserted entry or change topology; native Cordis composition applies them without changing core package versions. The installer retains the original patch bytes and order. Additional insert-entry fields (including `disabled`), extra override fields, non-finite numbers, YAML aliases and non-JSON tags are rejected before writes. Published bundles use the profile’s native `dsh.profile.bundles` selection and their original patch ids; updates remove any legacy Forge registration, so native controls and Forge share one instance. Updates preserve a native disabled selection and report `disabled`; installed-state queries read the current selection and live Loader entry. A native disabled entry reports `disabled` only after its fiber is inactive; an enabled entry that failed to import remains an activation failure. Plugins without bundle metadata use a Forge-owned profile patch row. Unrelated profile fields and patch rows remain intact.

The target’s required `sharedPackages` list distinguishes frontend-owned DSH/Cordis packages, Client platform packages and static runtime replacements from ordinary libraries in `hostPackages`. Regenerate the Forge target with the matching generation before building plugins. Ordinary dependencies use private packages resolved from their installation tree, even when the host inventory has a compatible version; peer requirements still validate their actual provider versions. Private transitive packages may share a name with an ordinary host library, while root plugin names cannot collide with any host or Client package. Each package records its own `hostDependencies`; the plan-wide `hostPackages` roster validates versions and does not grant imports to other packages. Importer-specific mappings expose those Host requirements, private dependencies and self references, preserving separate versions and fixed shared instances without filesystem symlinks. A stable entry wrapper references the current immutable package, letting Cordis HMR detect the file change. The immutable package retains its published entry path and resource paths, so `import.meta.url` resolves adjacent skills and data within that package. Host package subpath requests resolve to the immutable package and share its module cache; the bare root keeps the stable HMR wrapper. The public mirror exposes Client and resource files; updates remove obsolete mirrored resources after successful activation, and removal reports directory collection through the same VFS and batch notifications. Reconciliation requires the selected bundle’s actual entry id and confirms live activation. Failures retain package files and their diagnostics without promising restoration of the previous instance. Removal deselects and unloads the plugin before collecting unshared files; failed unloading retains its dependency and files.

Forge prepares declared dependency packages and delivers independently lowered module files, retaining their package-relative names and extensions. Loader aliases, computed `require()`, `require.resolve()` and computed `import()` select those prepared files at runtime; resolving a path alone does not evaluate its module. First loading evaluates the module, caches its exports and records the actual file dependency for HMR. Package-local CommonJS cycles use partial cached exports; cycles between Forge package artifacts remain unsupported. Runtime selection does not fetch missing packages or provide missing Node operations. Missing files, undeclared packages and unavailable operations fail when requested, so successful compilation does not establish successful activation or command execution. Files are downloaded into the VFS during installation even when never evaluated; this does not provide lazy downloads or reduce their RAM usage.

The configured Worker exposes a profile-scoped virtual `dsh plugin --profile <profile> add|update|remove <npm-package>` command through `node:child_process` and the model’s Bash shell. A shell process can call only host command names advertised at its startup; requests preserve its working directory, environment, pipeline input, filesystem and cancellation. Host command output is buffered until completion, then follows ordinary shell pipelines and redirection. Installation waits for Forge compilation, verified file application and Host reconciliation before reporting success. Synchronous calls can inspect local command/version metadata but cannot perform remote work. The preview forwards same-origin `/api/` and `/dsh-plugin-hub` Fetch requests to the Worker, including published plugins that call Host routes directly. Query strings, method, headers, body and cancellation are preserved; a same-origin Origin header is translated with the synthetic Host. Static assets, foreign origins and similar path names use the previous page Fetch. Route errors never retry against the static server. Synthetic requests share one Node-compatible Readable body across async iteration and `data`/`end`/`error` listeners; `setEncoding()` retains split character sequences. Aborting the exchange or completing its response cancels unread input.

Every file change uses ordinary VFS mutations. `ForgeInstaller.subscribe()` adds batch notifications for application and activation, while VFS subscribers observe individual writes and removals. Neither notification confirms durable storage. Forge mirrors installed root packages under the profile’s `node_modules`; `createRequire(anchor).resolve.paths()` exposes the anchor’s ancestor package directories so the standard bundle inventory discovers them without requiring a `./package.json` export. Without a persistence provider, installation state belongs to this Worker lifetime; with [browser persistence](#browser-persistence), applied artifacts and ownership are restored before boot. The [installer](src/forge/installer.ts) owns these operations and the [protocol validator](src/forge/protocol.ts) owns manifest admission.

### Build a local plugin

In the configured Worker preview, write source files and a `forge.json` under the session workspace, then run:

```sh
dsh plugin --profile web build ./greeting-source
```

The directory resolves against the shell working directory. Its `forge.json` declares `id`, npm package `name`, exact `version`, relative Host `entry` and a `files` array of relative source paths that includes the entry. Optional `dependencies` and `peerDependencies` maps default to empty objects; `peerDependenciesMeta` can declare optional peers. The command reads the selected JS, JSX, TS, TSX and JSON files through the invoking shell’s filesystem, submits their contents to Forge’s `/v1/builds`, verifies the artifacts and applies them through the existing installer. HTTP requests use the same replaceable provider as npm installs. This Worker compatibility command neither invokes a local Node compiler nor publishes an npm package. Host code runs in the Worker without browser DOM APIs.

To build a Client half, add `"client": { "entry": "client.tsx", "inject": ["@deepseek-ai/dsh-client-ui-conversation"] }` and include that entry and its local imports in the root `files`. `client.files` lists files used only by the browser, defaults to `[client.entry]`, must include that entry, and must be a subset of root `files` without the Host entry. Other submitted files remain Host compilation inputs, including modules loaded through computed requires; browser code can also import shared inputs. `client.inject` lists Client package graph dependencies and defaults to `[]`; the Client source’s exported `inject` separately names Cordis services such as `slots`. Optional `client.dependencies` and `client.peerDependencies` default to `{}` and declare additional browser requirements without granting those packages to Host code; root dependency declarations remain available to Host compilation. Root and Client declarations for the same package must use the same range text. Export ordinary Client `apply`/`inject` code; Forge emits the browser factory and generates `dsh.client` and `./client` metadata. The installer mirrors that artifact into the normal Client graph for loading and hot replacement. The root `package.json` remains generated and cannot be submitted as source. A successful build command reports Host activation, not confirmation that a Client component mounted; inspect the Client registration and exercise its visible behavior separately. In the preview, same-origin `/api/` Fetch requests use the Worker carrier. Its direct lane streams `text/event-stream` incrementally and buffers other response types until completion; use SSE for live Host updates or JSON for finite snapshots.

Keep the plugin `id` and package `name` stable when updating. Edit the source and rerun the build command; source edits alone do not rebuild installed artifacts. The installer owns the Loader registration and hot replacement. Source validation, download or compilation failure leaves the installed version unchanged; activation failure reports a nonzero exit and does not promise restoration of the previous instance. A disabled plugin stays disabled, and command success does not confirm durable storage. After verifying the behavior, use the page's explicit save action before reloading; it retains workspace source and installed artifacts in separate VFS paths. [forge/commands.ts](src/forge/commands.ts) and [forge/source.ts](src/forge/source.ts) own command parsing and source collection.

## Outbound HTTP providers

`createWorkerHost({ httpTransport })` accepts an instance-owned provider with `fetch(request: Request): Promise<Response>`. It serves image and lazy-archive downloads, Forge builds and artifacts, virtual `curl`, `node:https.get`, and VFS-module Fetch calls, including model providers and plugin `globalThis.fetch`. Omitting it uses platform Fetch. Module global aliases resolve to the same per-loader proxy; the real Worker global is unchanged. This is dependency injection, not a sandbox for untrusted JavaScript.

For a provider implemented on the page, pass it to `connectWorkerHost(worker, { httpTransport })`. A dedicated MessageChannel transfers request/response fields and ReadableStreams, and relays cancellation; functions stay on the page. Transfer failures and opaque responses fail explicitly rather than being buffered. The returned `disposeHttp()` aborts and detaches this provider; the caller retains Worker and tunnel ownership. Direct Worker embeddings own their provider's disposal and call `host.stop()` to abort active HTTP. Providers must honor `Request.signal`, including pending response bodies; host shutdown also cancels unread response streams.

Pass the same provider as the third argument to the preview's `mountForgePreview(serverUrl, hostFetch, httpTransport)` so its target and build requests use it too. This does not intercept page-global Fetch, source-chooser requests, browser script/image loading, WebSockets, or code that creates another JavaScript realm. The default provider remains subject to browser CORS; a future native RPC provider can supply its own HTTP implementation without changing plugin request calls.

## Known Limitations and Deferred Work

<a id="known-limitations-and-deferred-work"></a>

- **The worker composition writes plaintext session logs** (`compression: 'none'` in the image's home patch; ConfigEditor rejects edits to that row's config): it carries no Zstandard codec, so exported logs are `.jsonl`, never `.jsonl.zstd`.
- **Builtin modules expose different capability levels**: `implemented/` provides Worker behavior; `optional/` permits imports whose unavailable operations throw `ERR_FEATURE_UNAVAILABLE_ON_PLATFORM`; `mock/` supplies structural stubs. Forge module files resolve their imports when executed, so delivery does not establish that a builtin namespace or operation is usable. `node:dns` and `node:dns/promises` are optional namespaces: imports are silent, but result-order setters/getters and address lookup report the unavailable operation to the console and throw. Plugins may catch that error and continue; no DNS query, result-order change or successful no-op is provided. `node:v8` is also optional: importing its `getHeapStatistics` function succeeds, but calling it reports and throws the same platform-unavailable error. No synchronous heap statistics or fabricated memory values are supplied; plugins must handle unavailable measurements. `node:vm`, `node:net`, `node:sqlite` and `node:worker_threads` remain structural stubs.
- **`node:assert/strict` supports truthiness assertions only**: for falsy values, the callable default and `ok` throw `ERR_ASSERTION` with the supplied message or generic text, or rethrow a supplied Error unchanged. Other assertion APIs are absent.
- **Network compatibility uses the configured HTTP provider**: `node:https.get` supports registry metadata responses, and virtual `curl` supports the catalog/probe arguments used by Plugin Hub. The default provider follows browser CORS rules; process proxy settings, custom TLS options and synchronous network requests are unsupported.
- **Native response prototype patches do not affect the tunnel**: synthetic responses do not inherit `http.ServerResponse.prototype`; plugins that patch it for gzip or Brotli compression leave tunnel responses uncompressed.
- **Native TLS listeners require a Node Host**: the worker's `node:https.createServer` rejects activation rather than substituting plaintext. The preview's internal HTTP tunnel does not bind sockets; browser-facing HTTPS belongs to its deployment server.
- **Desktop product telemetry is unavailable**: `got.post` reports an explicit worker-host refusal. Got and its Node HTTP dependencies are excluded from the browser image; Desktop reporting remains disabled in the preview composition.
- **Package commands are limited to Forge plugin operations**: the Worker does not run pnpm, global npm installations, Git installs or arbitrary Node subprocesses. `execa` remains unavailable. [Forge](#forge-plugin-updates) resolves and compiles supported npm plugins on its server.
- **pi-ai model requests are unavailable**: the replacement exposes a fixed subset of installed provider identifiers with no models, allowing the adapter to register configuration metadata. Its identifiers must stay valid when pi-ai is upgraded; inference entry points report an explicit worker-host refusal.
- **PTC Node programs are unavailable**: the process shim exposes `/dsh/bin/node` as its executable identity so the provider can activate, but the Worker has neither a Node executable nor `stripTypeScriptTypes`. Program execution fails before launching a child.
- **Office conversion requires a Node Host**: the LibreOffice kit replacement rejects converter creation with `unavailable`. The browser image excludes the kit and its engine dependencies; the Office preview reports that conversion is unavailable.
- **Host HMR requires executable JavaScript**: the loader records file dependencies, including cache hits and deferred requires, and expires module records and package metadata for replacement. Configure HMR watch roots to reload VFS edits automatically; profile recomposition also checks loaded files. Bootstrap modules and their dependencies require a new Worker, as do changes to the Worker bundle or static module proxies. TS/TSX compilation, package installation, Client bundle replacement and durable saving are separate capabilities. The [Chrome-capable lifecycle test](../../../apps/web/tests/worker-hmr.e2e.ts) covers shared dependencies, entry removal and re-addition, failed imports and recovery without replacing the Worker.
- **The Node internal modules answer only their HMR-replaced members**: the CommonJS loader, package reader, `modules` binding, and `getOrCreateModuleJob` refuse when called, and the Worker's own `require` does not route through the CommonJS loader, so replacing `Module._resolveFilename` or `Module._load` does not change Worker resolution.
- **CommonJS `require('stream')` returns the module namespace, not Node's `Stream` constructor**: code that passes it to `util.inherits` fails at load.
- **A lazily supplied file has no synchronous read before its archive arrives**: a consumer must read it asynchronously first; the Host's on-demand Client chunk route does.
- **Filesystem watchers observe only the mounted VFS**: image seeding is silent and the VFS has no symlinks or external writers. `persistent`, `ref()`, and `unref()` preserve the Node API but cannot control a dedicated Worker's lifetime because browsers expose no ref-counted event loop.
- **Worker confinement is a VFS boundary, not kernel Landlock**: `read-only` and `workspace-write` run the unchanged `@deepseek-ai/node-addon-system/landlock-run` JavaScript and launcher argv, but the process layer implements the logical `landlock-run` executable and enforces its grants on every shell filesystem request. `full` therefore covers the Worker command table and mounted VFS only; it does not claim arbitrary native-process execution or Linux kernel isolation. Registered host commands can perform profile operations such as plugin installation; path grants apply to their source-file reads and do not sandbox activated JavaScript.
- **The worker bundle pins a path inside `@yarnpkg/parsers`** — the build resolves the package's own `lib/shell.js` instead of its root, whose barrel also re-exports the Syml parser and so drags js-yaml into a bundle that never parses that format (around 175 kB, plus its module body at worker start). The path is derived from the package manifest, so a layout change fails the build rather than reinstating the barrel; upgrading the dependency means re-checking that the shell parser still lives there.
- **The shell is not bash**: no loops, functions, `case`, job control, or process substitution — the grammar stops at pipelines, `&&`/`||`, subshells, groups, redirections, and expansion. `&` runs its command to completion in place, `sed` accepts only substitution scripts, patterns are JavaScript regular expressions, and the command table holds coreutils only (no `git`, no network tools).
- **A shell process has no synchronous filesystem**: it reads and writes the host's VFS by message, because blocking on a reply would need `SharedArrayBuffer`, which requires a cross-origin isolation GitHub Pages cannot grant. Directory-walking commands therefore cost one round trip per entry, and two concurrent commands can interleave their writes.
- **Transport, worker-host, and page-half coverage needs a browser-grade harness** — the per-file coverage gate is unmet for those modules; unit specs cover storage, ALS, the transform, and the stub contracts.
