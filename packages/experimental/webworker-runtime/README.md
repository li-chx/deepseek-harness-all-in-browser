# `@deepseek-ai/dsh-experimental-webworker-runtime`

English | [中文](README.zh.md)

## Summary

The browser worker host: the whole harness plugin tree runs inside one dedicated Web Worker, for preview deployments and packaging regressions ([experimental group](../README.md)). The worker inflates a packed VFS image off its download and mounts it in memory, loads its modules through a CommonJS wrapper loader, and serves the page over a postMessage tunnel that speaks plain HTTP. Use it when a preview must run the packaged harness without a Node host.

## Use this package

The public npm package exposes the runtime library at its root, the self-contained browser Worker at `./worker`, and the page connector at `./client`. Deployments supply and serve the VFS image separately through the [packer](../webworker-packer/README.md); installing this library does not add a profile layer. The root also exports the module-proxy and replacement tables used by the packer.

Three build artifacts and one source-owned process layer:

- **`lib/index.js` (assembly library)** — `createWorkerHost`/`startWorkerHost` mount the base image and any ordered data overlays (`storage/`), register the image's lazy archives, install the module loader (`module-system/`) and the `process` shim, boot the tree through the image's own `dsh-app-boot`, and hand the tunnel its serving seams. Overlays may replace files only under `home/` and `workspace/`; they cannot replace the base manifest or modules. The image layout contract (`image-layout.ts`: virtual root, manifest path, lazy archive directory, empty directories) and the manifest (`image-manifest.ts`: profile, installation, the `lowered` wrapper-contract gate, lazy archives) are shared with the packer. The Worker boots the manifest's shipped profile as the launcher does: the image's app-boot initializes `home/profiles/<profile>/` from the shipped template, resolves bundles from the installation manifest the image carries alone, and composes the bundle layers, the profile patch, and the home patch. The profile context, the launch environment snapshot, and a `PluginPackages` service without a runtime resolution are provided as the launcher provides them; the Worker loader owns module resolution. The profile context carries no command-line overlay; the image's home patch (`home/cordis.patch.yml`), which the packer writes from `PLATFORM_ENTRY_CONFIG`, keeps JSONL Session logs plaintext. ConfigEditor persists overrides in the profile patch, reconciles each write, and Loader commits live values. The Worker commits `appReady` once the tunnel serves. Its `hmrModules` provider connects the Worker module cache to [profile HMR](../../boot/hmr/README.md), so configuration and loaded code changes share the existing reload queue. Plugin management lists and switches the installation's optional bundles, and its package operations fail with the `execa` refusal. Configuration edits last for the current Worker lifetime.
- **Lazy archives** — the manifest registers each page chunk the packer moved out of the base image by path and size, with its archive name relative to the image URL. Existence, stats, and listings answer at once; the first asynchronous read (`fs.promises.readFile`, `fs.promises.open`, `fs.createReadStream`, `fs.promises.cp`) fetches and inflates that archive once for every waiting reader, checks it against the registration, and mounts its files without publishing a mutation. A failed fetch rejects the read and leaves the files registered, so the next read fetches again. Until then, synchronous reads, writes, appends, truncation, chmod, rename, and link of a registered file fail with `ERR_DSH_VFS_DEFERRED` naming the archive; unlink and recursive removal drop the registration, and seeding the path replaces it. The archive name derives from its content digest, and the fetch checks only the registered paths and sizes, not the digest. An image that registers lazy archives must be passed as a URL.
- **`lib/worker.js` (worker bundle)** — the assembly plus this package's Node-compatibility layer as one self-contained ES module. The module proxy table (`module-proxies.ts`) is the only platform fork: `node:*` builtins over VFS/tunnel/browser primitives, structural stubs that fail loud on the console for what a browser cannot do, and native/binary package replacements. `node:module` supplies `createRequire().resolve` and `.resolve.paths()` over the image package root, so unchanged packages can discover manifests without evaluating their modules. `node-addon-require-builtin` answers the Node v24.18.0 internal modules that the vendored Loader, app-boot, and HMR read without `--expose-internals`: the cascaded ESM loader's `resolveSync` and `import` over the Worker loader, with Node's `ERR_MODULE_NOT_FOUND` and `ERR_PACKAGE_PATH_NOT_EXPORTED` codes, and an empty `loadCache`; and the CommonJS loader, package reader, `modules` binding, and resolve-cache members that HMR replaces, which refuse when called. `process.versions.node` reports `24.18.0`, so `ModuleLoader.fromInternal()` and the Loader's `internal` reach that cascaded loader. `node:path.win32.isAbsolute` and `node:util.inherits` follow Node; other `win32` members throw. The `node:util` JSON-data comparator compares own enumerable properties, preserving Node admission decisions for recorded fields such as `__proto__`. The global `process` shim carries Node detection fields including `title`, preventing Worker execution from entering DOM-only branches. The pack-time parser reports statically named module requests, including module-scope direct calls of the form `createRequire(import.meta.url)('pkg')` through a named `node:module` or `module` import, to the packer's reachability walk. Stored, CommonJS-obtained, and rebased `createRequire` calls require image entry seeds. VFS mutations drive `node:fs` callback, polling, and promise watchers, whose listeners run in the async context where the watcher was created rather than that of the writing code; open descriptors retain file identity and access mode across rename, replacement, and unlink, `FileHandle.stat({ bigint: true })` reports the same device and inode identity as a path stat while the name still refers to that file, and `FileHandle.chmod()` updates the opened file identity; `readable-stream` supplies `node:stream/promises` completion and pipeline helpers and the stream state machine used by file streams and unchanged image packages such as Chokidar and readdirp. `node:string_decoder` uses the maintained npm decoder to retain incomplete UTF-8 and UTF-16 characters across stream chunks. AsyncLocalStorage carries sync-stack causality across `await` through the snapshot/restore faces the pack-time lowering injects. The worker holds no compiler: an image the packer did not lower is refused at mount. The callback `fs.realpath.native` alias resolves within the mounted VFS and supports `util.promisify`.
- **`src/shell/` (the worker's own process layer)** — a browser worker cannot fork, so `node:child_process` is not a stub but an implementation: `spawn` starts the command in its own Web Worker — this same bundle, told by its first frame to be a shell process — and reports it through the `ChildProcess` surface the subprocess service consumes. The command runs off the host's thread, `SIGKILL` terminates it whatever it is doing, and it reaches the VFS only by message (the host serves those frames). Worker platform executables preserve native-package protocols such as Landlock without replacing their JavaScript packages or coupling their implementations to `node:child_process`; `xdg-open` sends one VFS text file to the page's read-only viewer, so desktop-opener actions such as **Open configuration file** show the file in the page; ordinary commands use the package's evaluator and coreutils command table. The grammar is `@yarnpkg/parsers`' `parseShell`, while `execSync`/`fork` still refuse because they need a real process.
- **`lib/client.js` (page half)** — startup has two independent stages. `chooseWorkerHostSource({ image?, fixtureManifest? })` optionally owns the boot barrier and fixture manifest: without `preview-fixture` it waits at the source chooser, while a valid query selects directly; either path returns ordered overlays. `connectWorkerHost(worker, { image?, overlays? })` remains the public base-runtime connector; callers that skip the chooser get an empty overlay list. `apps/web` invokes both and supplies its statically bundled Worker. The opening `init` frame carries the base and ordered overlay URLs, the boot payload delivers the structured index-injection table, and `applyIndexInjections` executes it before the shell entry runs. Script preload rows are advisory and skipped because `/plugins` resources resolve only through the tunnel; `loadBundle` fetches each combo on first demand, embeds its tunnel-only source map as a Base64 data URL, and executes the script as a Blob. The worker's unsolicited `view-text` frame opens the page's modal text viewer. The tunnel also exposes fetch-shaped transport, the independent file-upload carrier, and the API client. Request frames preserve Blob bodies through structured clone and transfer `ReadableStream<Uint8Array>` ownership. The Host Worker streams both forms into the route, so neither browser thread creates a complete byte array for a generic-file upload. A Remote stream's uplink crosses as `stream-uplink-item` / `stream-uplink-end` frames into an unbounded `TunnelUplink` that drops items arriving after `end`: the page and its worker are one trusted same-origin boundary, so the Host inbox cap does not apply.

Callbacks and timers registered under an explicit root context retain its empty stores, so they cannot inherit an unrelated transaction.

Acceptance lives in `apps/web/tests/preview-boot.e2e.ts`, which serves the real built pages and drives the pre-boot chooser plus Worker activation in headless Chromium. The empty selection exercises first-run startup. The `vfs-example` overlay supplies ordinary workspace files and plaintext persistence artifacts for cold Workspace/Session discovery, tool presentation, subagent navigation, and history paging without a model request. The showcase mixes empty, whitespace-only, and non-empty reasoning with a long multiline command and a parent-path file link; these are authored fixtures, not live model output. The [packer](../webworker-packer/README.md) prepares current-generation successors from committed historical logs in Node; those source logs remain byte-identical in the overlay. The fixture generator owns the acceptance test's current projection cache. The chooser reserves WebFS as a separate user-authorized source; that provider does not read the built-in fixture.

The [built-bundle import sweep](tests/compile/transform-corpus-check.ts) checks bare Node imports after the library build. Its Dockkit exception accepts Node’s unknown-`.css`-extension refusal for any stylesheet rather than one pinned path; another extension, error code, or message, and an unexpectedly successful exempt import, remain errors.

## Forge plugin updates

The optional preview control opens with `?forge=<HTTP service URL>`. **DSH Forge** submits TypeScript Host plugin sources or an npm package specification to that service and applies its compiled manifest through the running Worker. The rc.2 frontend embeds `FORGE_GENERATION = 'dsh-worker-rc2-6'`; it rejects artifacts from other generations before downloads or writes. The service must target that generation and the base image's exact host package versions. Core packages and shared host modules remain owned by the frontend build. The target separately declares `clientPackages`, captured from the trusted base image before overlays; these exact page-shared versions satisfy Client requirements without granting Host imports. Missing or mismatched Client requirements and attempts to replace shared Client packages fail before file writes. Published packages with a supported single-entry `dsh.bundle` patch can carry their existing Client bundle; package metadata and assets enter the normal Client graph and HMR path.

The installer verifies the complete manifest, supported bundle patch and missing artifact bytes before changing files. Supported bundle patches contain exactly one `insert` of their own package, with `id`, `name`, and optional JSON-compatible literal `config` (objects, arrays, scalars or null), whose schema is validated by the plugin. The same patch may override existing root entries using unique `id` values and literal `config`, `disabled` (boolean or null), or both. Overrides cannot target the inserted entry or change topology; native Cordis composition applies them without changing core package versions. The installer retains the original patch bytes and order. Additional insert-entry fields (including `disabled`), extra override fields, non-finite numbers, YAML aliases and non-JSON tags are rejected before writes. Published bundles use the profile’s native `dsh.profile.bundles` selection and their original patch ids; updates remove any legacy Forge registration, so native controls and Forge share one instance. Updates preserve a native disabled selection and report `disabled`; installed-state queries read the current selection and live Loader entry. A native disabled entry reports `disabled` only after its fiber is inactive; an enabled entry that failed to import remains an activation failure. Plugins without bundle metadata use a Forge-owned profile patch row. Unrelated profile fields and patch rows remain intact.

Importer-specific package mappings support separate dependency versions without filesystem symlinks. A stable entry wrapper references the current immutable package, letting Cordis HMR detect the file change. The immutable package retains its published entry path and resource paths, so `import.meta.url` resolves adjacent skills and data within that package. The public mirror keeps its root wrapper separate from the implementation and exposes Client and resource files; updates remove obsolete mirrored resources after successful activation, and removal reports directory collection through the same VFS and batch notifications. Reconciliation requires the selected bundle’s actual entry id and confirms live activation. Failures retain package files and their diagnostics without promising restoration of the previous instance. Removal deselects and unloads the plugin before collecting unshared files; failed unloading retains its dependency and files.

The configured Worker exposes a profile-scoped virtual `dsh plugin --profile <profile> add|update|remove <npm-package>` command through `node:child_process`. Installation waits for Forge compilation, verified file application and Host reconciliation before reporting success. Synchronous calls can inspect local command/version metadata but cannot perform remote work. The preview forwards same-origin `/api/` and `/dsh-plugin-hub` Fetch requests to the Worker, including published plugins that call Host routes directly. Query strings, method, headers, body and cancellation are preserved; a same-origin Origin header is translated with the synthetic Host. Static assets, foreign origins and similar path names use the previous page Fetch. Route errors never retry against the static server. Synthetic requests share one Node-compatible Readable body across async iteration and `data`/`end`/`error` listeners; `setEncoding()` retains split character sequences. Aborting the exchange or completing its response cancels unread input.

Every file change uses ordinary VFS mutations. `ForgeInstaller.subscribe()` adds batch notifications for application and activation, while VFS subscribers observe individual writes and removals. Neither notification confirms durable storage. Forge mirrors installed root packages under the profile’s `node_modules`; `createRequire(anchor).resolve.paths()` exposes the anchor’s ancestor package directories so the standard bundle inventory discovers them without requiring a `./package.json` export. Installation state belongs to this Worker lifetime; refreshing the page discards it. The [installer](src/forge/installer.ts) owns these operations and the [protocol validator](src/forge/protocol.ts) owns manifest admission.

## Outbound HTTP providers

`createWorkerHost({ httpTransport })` accepts an instance-owned provider with `fetch(request: Request): Promise<Response>`. It serves image and lazy-archive downloads, Forge builds and artifacts, virtual `curl`, `node:https.get`, and VFS-module Fetch calls, including model providers and plugin `globalThis.fetch`. Omitting it uses platform Fetch. Module global aliases resolve to the same per-loader proxy; the real Worker global is unchanged. This is dependency injection, not a sandbox for untrusted JavaScript.

For a provider implemented on the page, pass it to `connectWorkerHost(worker, { httpTransport })`. A dedicated MessageChannel transfers request/response fields and ReadableStreams, and relays cancellation; functions stay on the page. Transfer failures and opaque responses fail explicitly rather than being buffered. The returned `disposeHttp()` aborts and detaches this provider; the caller retains Worker and tunnel ownership. Direct Worker embeddings own their provider's disposal and call `host.stop()` to abort active HTTP. Providers must honor `Request.signal`, including pending response bodies; host shutdown also cancels unread response streams.

Pass the same provider as the third argument to the preview's `mountForgePreview(serverUrl, hostFetch, httpTransport)` so its target and build requests use it too. This does not intercept page-global Fetch, source-chooser requests, browser script/image loading, WebSockets, or code that creates another JavaScript realm. The default provider remains subject to browser CORS; a future native RPC provider can supply its own HTTP implementation without changing plugin request calls.

## Known Limitations and Deferred Work

<a id="known-limitations-and-deferred-work"></a>

- **The worker composition writes plaintext session logs** (`compression: 'none'` in the image's home patch; ConfigEditor rejects edits to that row's config): it carries no Zstandard codec, so exported logs are `.jsonl`, never `.jsonl.zstd`.
- **Builtin import admission is classified by implementation path**: `implemented/` provides Worker behavior; `optional/` permits imports whose unavailable operations throw `ERR_FEATURE_UNAVAILABLE_ON_PLATFORM`; `mock/` remains excluded from Forge plugin builds. `node:dns` and `node:dns/promises` are optional namespaces: imports are silent, but result-order setters/getters and address lookup report the unavailable operation to the console and throw. Plugins may catch that error and continue; no DNS query, result-order change or successful no-op is provided. `node:v8` is also optional: importing its `getHeapStatistics` function succeeds, but calling it reports and throws the same platform-unavailable error. No synchronous heap statistics or fabricated memory values are supplied; plugins must handle unavailable measurements. `node:vm`, `node:net`, `node:sqlite` and `node:worker_threads` remain structural stubs.
- **`node:assert/strict` supports truthiness assertions only**: for falsy values, the callable default and `ok` throw `ERR_ASSERTION` with the supplied message or generic text, or rethrow a supplied Error unchanged. Other assertion APIs are absent.
- **Network compatibility uses the configured HTTP provider**: `node:https.get` supports registry metadata responses, and virtual `curl` supports the catalog/probe arguments used by Plugin Hub. The default provider follows browser CORS rules; process proxy settings, custom TLS options and synchronous network requests are unsupported.
- **Native response prototype patches do not affect the tunnel**: synthetic responses do not inherit `http.ServerResponse.prototype`; plugins that patch it for gzip or Brotli compression leave tunnel responses uncompressed.
- **Native TLS listeners require a Node Host**: the worker's `node:https.createServer` rejects activation rather than substituting plaintext. The preview's internal HTTP tunnel does not bind sockets; browser-facing HTTPS belongs to its deployment server.
- **Desktop product telemetry is unavailable**: `got.post` reports an explicit worker-host refusal. Got and its Node HTTP dependencies are excluded from the browser image; Desktop reporting remains disabled in the preview composition.
- **Package commands are limited to Forge plugin operations**: the Worker does not run pnpm, global npm installations, Git installs or arbitrary Node subprocesses. `execa` remains unavailable. [Forge](#forge-plugin-updates) resolves and compiles supported npm plugins on its server.
- **pi-ai model requests are unavailable**: the replacement exposes a fixed subset of installed provider identifiers with no models, allowing the adapter to register configuration metadata. Its identifiers must stay valid when pi-ai is upgraded; inference entry points report an explicit worker-host refusal.
- **PTC Node programs are unavailable**: the process shim exposes `/dsh/bin/node` as its executable identity so the provider can activate, but the Worker has neither a Node executable nor `stripTypeScriptTypes`. Program execution fails before launching a child.
- **Office conversion requires a Node Host**: the LibreOffice kit replacement rejects converter creation with `unavailable`. The browser image excludes the kit and its engine dependencies; the Office preview reports that conversion is unavailable.
- **Host HMR requires executable JavaScript**: the loader records file dependencies, including cache hits and deferred requires, and expires module records and package metadata for replacement. Configure HMR watch roots to reload VFS edits automatically; profile recomposition also checks loaded files. Bootstrap modules and their dependencies require a new Worker, as do changes to the Worker bundle or static module proxies. TS/TSX compilation, package installation, Client bundle replacement and durable saving are separate capabilities. The [Chrome-capable lifecycle test](../../../apps/web/tests/worker-hmr.e2e.ts) covers shared dependencies, entry removal and re-addition, failed imports and recovery without replacing the Worker.
- **The Node internal modules answer only their HMR-replaced members**: the CommonJS loader, package reader, `modules` binding, and `getOrCreateModuleJob` refuse when called, and the Worker's own `require` does not route through the CommonJS loader, so replacing `Module._resolveFilename` or `Module._load` does not change Worker resolution.
- **CommonJS `require('stream')` returns the module namespace, not Node's `Stream` constructor**: code that passes it to `util.inherits` fails at load.
- **A lazily supplied file has no synchronous read before its archive arrives**: a consumer must read it asynchronously first; the Host's on-demand Client chunk route does.
- **Filesystem watchers observe only the mounted VFS**: image seeding is silent and the VFS has no symlinks or external writers. `persistent`, `ref()`, and `unref()` preserve the Node API but cannot control a dedicated Worker's lifetime because browsers expose no ref-counted event loop.
- **Worker confinement is a VFS boundary, not kernel Landlock**: `read-only` and `workspace-write` run the unchanged `@deepseek-ai/node-addon-system/landlock-run` JavaScript and launcher argv, but the process layer implements the logical `landlock-run` executable and enforces its grants on every shell filesystem request. `full` therefore covers the Worker command table and mounted VFS only; it does not claim arbitrary native-process execution or Linux kernel isolation.
- **The worker bundle pins a path inside `@yarnpkg/parsers`** — the build resolves the package's own `lib/shell.js` instead of its root, whose barrel also re-exports the Syml parser and so drags js-yaml into a bundle that never parses that format (around 175 kB, plus its module body at worker start). The path is derived from the package manifest, so a layout change fails the build rather than reinstating the barrel; upgrading the dependency means re-checking that the shell parser still lives there.
- **The shell is not bash**: no loops, functions, `case`, job control, or process substitution — the grammar stops at pipelines, `&&`/`||`, subshells, groups, redirections, and expansion. `&` runs its command to completion in place, `sed` accepts only substitution scripts, patterns are JavaScript regular expressions, and the command table holds coreutils only (no `git`, no network tools).
- **A shell process has no synchronous filesystem**: it reads and writes the host's VFS by message, because blocking on a reply would need `SharedArrayBuffer`, which requires a cross-origin isolation GitHub Pages cannot grant. Directory-walking commands therefore cost one round trip per entry, and two concurrent commands can interleave their writes.
- **Transport, worker-host, and page-half coverage needs a browser-grade harness** — the per-file coverage gate is unmet for those modules; unit specs cover storage, ALS, the transform, and the stub contracts.
